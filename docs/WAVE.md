### Этап 1. Данные: теги в кэше, артисты списком, единая оценка исхода

**1.1. Теги в `tracks`.** Миграция № 6: `ALTER TABLE tracks ADD COLUMN tags TEXT;`
`upsert_tracks` пишет `tags = COALESCE(?новое, tags)` — пустое значение старые теги не затирает.
Все чтения трека из кэша возвращают `tags`. Обновить `docs/DB.md`.

Старые лайки останутся без тегов, пока трек не придёт с сервиса заново. Если в `services.rs` уже есть
получение треков пачкой по ref — при первом запросе порции за запуск дозаправить в фоне до 50 лайков
без тегов (ошибки молча). Если такого метода нет — не писать его, профиль наполнится сам.

**1.2. Артисты трека.** Новая функция `artist_keys(t: &Track) -> Vec<String>`: имена из `t.artists`
(нижний регистр, обрезанные пробелы), а если список пуст — одна строка `t.artist`. Первый ключ —
главный. Строки **не резать** по запятым и `&` («Tyler, The Creator», «Simon & Garfunkel»).

- Лимиты разнообразия (подряд, в порции, за сессию, пауза) — по главному ключу.
- Вкус (Томпсон, лайкнутый артист, время суток) — лучший из всех ключей трека.
- В `store/wave.rs` артисты для `plays` / `skips` / лайков берутся через `JOIN tracks` из
  `artists_json`; строки без записи в `tracks` — по сохранённой строке `artist`, как сейчас.
- Интерфейс шлёт в запросе главный ключ так же, как Rust (взять первого из `track.artists`).

**1.3. Оценка исхода.** Одна функция, одинаковая в TS и Rust (`reward`), тесты на обе:

| Что случилось (`f` = прослушано / длительность) | Оценка |
|---|---|
| 👎 | −2 (и бан трека, как сейчас) |
| лайк во время трека или трек уже в Любимых | +1.5, отменяет минусы |
| ручной пропуск, `f < 0.25` или прослушано < 30 с — «ранний пропуск» | −1 |
| ручной пропуск, `0.25 ≤ f < 0.5` | −0.4 |
| ручной пропуск, `0.5 ≤ f < 0.8` | 0 |
| `f ≥ 0.8` (как угодно закончился) | +1 |
| трек сменился не пропуском и `f < 0.8` | 0 |

Длительность 0 — считать по секундам: < 30 с — ранний пропуск, ≥ 150 с — дослушан.

- «Артист на паузе» — по-прежнему два **ранних** пропуска подряд.
- В `skips` теперь пишется любой ручной пропуск в волне с оценкой < 0 (сейчас — только до 30 с).
  Комментарий в `docs/DB.md` поправить.
- Сиды сессии («зашло») — оценка ≥ +1.

**Проверка:** тесты `artist_keys` (совместный трек Яндекса, пустой список), `reward` (каждая строка
таблицы), миграция на базе со старой схемой, теги не затираются пустым значением.

### Этап 2. Вкус 2: затухание, штраф треку, профиль тегов

Всё в `store/wave.rs` `taste()`, окно — 180 дней.

**2.1. Затухание.** Вес события `w = 0.5 ^ (возраст_в_днях / 30)`.

**2.2. Артист.** `pos[a] = Σ w · p`, где `p = 1` для прослушивания с `f ≥ 0.8` и `0.4` для остальных
строк `plays`; `neg[a] = Σ w · |оценка|` по `skips` (оценка — по `played_ms` и длительности из
`tracks`, нет длительности — 1). `Taste.plays / skips` становятся `f64`. Томпсон:
`beta(1 + round(pos), 1 + round(neg))` — выборщик не менять.

**2.3. Штраф треку.** `Taste.track_skips: HashMap<ref, f64>` — сумма `w · |оценка|` по пропускам
самого трека.

**2.4. Профиль тегов.** Новый разбор `tag_set(t) -> Vec<String>` вместо `tag_words`:
- фразы в кавычках из `tag_list` SoundCloud — один тег (`"drift phonk"`), остальное — по пробелам и
  запятым; жанр — тоже тег;
- склейка написаний: `hip-hop / hip hop / hiphop`, `lo-fi / lofi`, `r&b / rnb`,
  `drum & bass / drum and bass / dnb`, `k-pop / kpop` (таблица-константа рядом с `MOODS`);
- выбросить мусор: короче 3 знаков, числа и годы, `music, new, free, download, soundcloud, official,
  audio, song, track, beat, beats, prod, remix`, совпадение с именем артиста;
- не больше 8 тегов с трека.

`mood_fit` оставить на подстроках как есть.

Профиль: для тега `pos_t` и `neg_t` из трёх источников — лайки (вес 1.5, затухание по `added_at` с
полупериодом 90 дней, не ниже 0.3), прослушивания (как в 2.2), пропуски (как в 2.2).
`p0` — общая доля плюсов: `Σpos / (Σpos + Σneg)`; нет минусов — 0.8.
Оценка тега: `v_t = (pos_t + 5·p0) / (pos_t + neg_t + 5) − p0`. Теги с `pos_t + neg_t < 2` не считать.
Оценка трека `profile_fit` = среднее `v_t` по известным тегам × 2, обрезать до −1…1; известных нет — 0.
В `Taste` хранить готовую карту `tag → v_t`.

**Проверка:** свежее событие весит больше старого; тег с одними пропусками — минус; тег, который есть
у всего подряд, — около нуля; `"drift phonk"` — один тег; `hip-hop` и `hiphop` — один тег.

**Сделано 2026-11-16 — только профиль тегов (2.4); затухание артистов (2.1–2.3) и штраф треку — нет**
(`wave.rs` `parse_tags` / `tag_set` / `tags_fit`, `store/wave.rs` `tag_profile` / `tag_values`).
Отличия от текста выше, по решению владельца и по ходу работы:
- **Годы остаются:** `2016` — метка эпохи и сцены (как `lil peep`, `onda andar`), выбрасываются только
  остальные числа. Имя артиста выбрасывается лишь на **его** треке; на чужом оно — метка сцены.
  Жанр через «/» (`R&B/Soul`) делится на два тега.
- **Профиль у каждого настроения свой.** Кроме общего (лайки, прослушивания, пропуски, 👎; окно 180
  дней, полураспад 30) считается профиль режима из `wave_events`: чем кончались треки с тегом
  именно в «Грустной» / «Жёсткой» / «Спокойной» / «Весёлой» волне. Он идёт отдельным признаком
  `mode_profile` (вес 1.5, как у словаря `mood_fit`): словарь остаётся подсказкой на старте, а
  `gothboiclique` в «Грустной» выучится сам, когда его начнут дослушивать. Нет событий — признак 0.
- Теги пропущенных треков сессии идут в минус (`skipped_tracks` в запросе, вес вдвое слабее, чем у
  зашедших); `session_tags` теперь −0.9…0.9.
- 👎 входит в профиль как минус 2.0 (сильнее любого пропуска).
- Веса `profile_fit` 1.2 / 0.8 / 0.6 (Своя / настроения / Незнакомое) — стартовые, «на глаз»;
  менять их можно только по цифрам `wave_stats`.

**Затухание и штраф треку сделаны 2026-11-16** (`store/wave.rs` `taste`): `Taste.plays / skips` —
`f64`-суммы с затуханием (окно 180 дней, полураспад 30), `track_skips` — штраф каждому треку; признак
`track_skips` (вес −1.2 во всех режимах). Этап 2 закрыт.

### Этап 4. Кандидаты: свои лайки, второй шаг, взвешенные сиды, кэш похожих

> - популярные треки 1–2 любимых / слушаемых артистов в котле (`Core::artist_top`,

**4.1. «Забытые любимые».** Запрос в `store/wave.rs`: лайкнутые треки, которые не играли 30 дней
(или ни разу), без 👎, не из `exclude`, с записью в `tracks`. Из них взять до 40, оценить

| Режим | Сколько своих в порции из 10 |
|---|---|
| Своя | 3 |

| Незнакомое | 0 |

Сборка порции: сначала `pick` на `n − k` новых, потом свои вставляются на места 2, 5, 8 (с нуля).
Правило «не два одного артиста подряд» при вставке сохраняется: место не подходит — сдвинуть на
следующее, не нашлось — трек не ставить. Первая порция сессии начинается с нового трека, не со
своего. Своих не хватило — порция добирается новыми.

**4.2. Второй шаг (разведка).** После первого круга `similar` взять кандидатов с лучшим `rank` от
артистов, которых нет во вкусе, и запросить `similar` уже от них: «Своя» — 1 запрос, «Незнакомое» —
3, настроение и волна по треку — 0. Их кандидаты идут в общий пул с `rank × 0.6`.

**4.3. Сиды с весом.** Вместо равномерного `rng.sample` — выборка без повторов с весами:
`вес = 0.85 ^ место` (0 — самый свежий), × 1.5, если трек и лайкнут, и дослушан. С этапа 6 —
× 0.3 для сида, чьи предложения пропускали чаще 60 % (не меньше 5 исходов за 30 дней).
В `Rng` добавить `weighted_sample`.

**4.4. Кэш похожих.** Список `similar` по ref хранить 24 часа. Сначала посмотреть, как устроена
таблица `catalog` (`ref, kind, json, fetched_at`): подходит — класть туда с `kind = 'similar'`; не
подходит — кэш в памяти в `Core` (не больше 300 списков). Ряд «Похожее» на главной
(`similar_tracks`) ходит через тот же кэш. Ошибки сети не кэшировать.

**Проверка:** в «Своей» при достатке лайков ровно 3 своих и не на первом месте первой порции; в
«Незнакомом» своих нет; повторный запрос порции с теми же сидами не ходит в сеть (тест на кэш);

### Этап 5. Реакция на серию пропусков

Интерфейс, `my-wave.svelte.ts`: два ранних пропуска подряд (любых артистов) —
1. из очереди убрать ещё не игравшие треки, кроме следующего (сначала посмотреть, что умеет
   `player`; нет удаления хвоста — добавить маленький метод, не ломая перемешивание и повтор);
2. сразу запросить порцию с актуальной `history`;
3. убранные треки вернуть из `served` (иначе они навсегда выпадут из сессии), счётчик серии обнулить.

Не чаще раза в 60 секунд. В волне по треку — так же, стиль (`seed`) остаётся.

**Проверка:** vitest на логику серии (2 ранних — пересбор, пропуск + дослушал + пропуск — нет,
защита 60 с).

**Сделано 2026-11-16** (`player/skip-series.ts`, `my-wave.svelte.ts` `rebuild` / `refill`,
`player.dropUpNext`, `queue.ts` `dropUpcoming(…, keep)`): ранним пропуском считается ручной
пропуск с оценкой ≤ −1, то есть и 👎. Свои «В очередь» пользователя пересборка не трогает — убираются
только треки, которые выдала волна. Порция, запрошенная до пересборки, выбрасывается (`epoch`);
то же теперь верно при повторном запуске волны (раньше запоздавшая порция дописывалась в новую
очередь).

### Этап 6. Измерение

Миграция № 7, таблица только локальная (в синк не идёт — пометить в `docs/DB.md`):

```sql
CREATE TABLE wave_events (
  id INTEGER PRIMARY KEY, user_id TEXT NOT NULL, session_id TEXT NOT NULL, ref TEXT NOT NULL,
  artist TEXT NOT NULL, mode TEXT NOT NULL,
  source TEXT NOT NULL,            -- similar / hop2 / liked / artist / seed
  seed_ref TEXT,                   -- от какого сида пришёл
  features_json TEXT,              -- Features на момент выдачи
  served_at INTEGER NOT NULL,
  reward REAL, listened_ms INTEGER, ended_at INTEGER   -- пусто, пока трек не сыгран
);
CREATE INDEX wave_events_time ON wave_events(user_id, served_at);
CREATE INDEX wave_events_ref ON wave_events(session_id, ref);
```

- `wave_portion` пишет строку на каждый выданный трек. Заранее подобранная порция для главной
  (`prefetch`) пишется тоже — без исхода она в подсчёт не попадает.
- `wave_feedback` получает событие `end { session_id, ref, listened_ms, reward }` — интерфейс шлёт
  его на конец **каждого** трека волны. Событие `skip` остаётся для таблицы `skips`.
- Строки старше 180 дней удалять при запуске.
- Команда `wave_stats(days)`: по режимам и по источникам — сыграно, доля ранних пропусков, доля
  дослушанных, средняя оценка. Экрана под неё **не делать** — только команда и тест; показывать
  решим с владельцем отдельно.
- Вес сидов из 4.3 читает эту таблицу.

Подбор весов по этим данным — отдельная задача после ~500 исходов, в эту работу не входит.

**Сделано 2026-11-16** (`store/wave_events.rs`, миграция № 7, `commands.rs` `wave_portion` /
`wave_feedback` / `wave_stats`, `my-wave.svelte.ts`). Чтобы писать в `features_json` признаки, `score`
разобран так, как описано в этапе 3: `Features` × `Weights`, веса режимов — ровно прежние числа
(`score_matches_legacy_formula` сверяет новую оценку со старой формулой на всех режимах). Источник
пока всегда `similar`: `hop2` и `liked` появятся вместе с этапом 4. Заранее подобранная порция для
главной (`prefetch`) пишется под своей сессией, и когда `start()` берёт её, исходы ложатся в те же

(дослушал или лайкнул), «ранних пропусков» — оценка ≤ −1.

## 3а. Синхронизация между устройствами аккаунта (решение 2026-11-16, не сделано)

Синк устройств одного аккаунта — в планах, поэтому журнал волны должен в него войти (раньше «только
локально»). Профили тегов и признаки **не синхронизируются**: они пересчитываются из сырых событий,
значит, после синка события дадут общий профиль на всех устройствах аккаунта. Профили разных
аккаунтов не смешиваются.

**Миграция № 8 (до серверной части):** выпущенную № 7 не править.
- `id` — текстовый, глобально уникальный (`new_id("we")`, как у плейлистов), а не автономер: на
  разных устройствах числа совпадут.
- `device_id TEXT NOT NULL` — откуда событие; `rev INTEGER NOT NULL` — глобальный счётчик синка
  (`next_rev`), как у лайков.
- События неизменяемы: строка дописывается при выдаче, один раз получает исход (`reward`,
  `listened_ms`, `ended_at`). Конфликтов слияния почти нет: слияние — «догрузить недостающие по id»;
  строку с исходом предпочитать строке без исхода. Tombstone `deleted` нужен только для подрезки
  старше 180 дней, чтобы удалённое не возвращалось с другого устройства.
- Размер: `features_json` ≈ 400 байт на трек, за 180 дней — десятки МБ на пользователя при лимите
  1–2 ГБ на всех. В синк идут события **без** `features_json` (его можно пересчитать или не
  хранить), либо сервер усекает признаки. Решить до протокола синка.
- Тип синка — `wave_event` в `POST /sync/push` / `GET /sync/pull` (`docs/API.md` §синк).
