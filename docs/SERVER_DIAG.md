# Диагностика доступности `try-sonar.ru` — отчёт

2026-11-26, задание — `docs/SERVER_DIAG_PROMPT.md`. Симптом владельца: сайт **открывается один раз**, после обновления страницы
или «Проверить обновление» в приложении не работает ничего на `try-sonar.ru`, а бот в Telegram работает.

**Коротко.** Корень пока **не найден**: с пути владельца (его телефон, его сети) замеров ещё нет, а со всех остальных путей
сервер отвечает. Код, который мог так себя вести, проверен: банов по IP у нас нет, лимит есть только на `/api` и отвечает
JSON 429, сайт без лимита. Починено то, что было видно в коде (блокирующий DNS в запросе, слепой access-лог), и сделаны
инструменты, которые покажут, где рвётся: страница `/diag`, `GET /api/diag`, монитор event loop, байты и обрывы в логе.
Дальше — ход владельца (раздел 5).

## 2. Гипотезы

| № | Гипотеза | Статус | На чём основано |
|---|---|---|---|
| H1 | Путь «оператор → хостинг» режет трафик (обрыв после ~16 КБ, DPI) | **не проверена** | С пути владельца замеров нет. Против простого варианта: главная весит 88 КБ и в первый раз открылась — значит, тогда либо пришла из кэша, либо по другой сети, либо режут не по размеру. Таблица `/diag` покажет размер обрыва, если он есть |
| H2 | Прокси хостинга (nginx) режет клиента после всплеска соединений: лимит на IP, репутация, keep-alive | **не проверена, лучше всех ложится на симптом** | «Первый раз да, потом всё и на все соединения» — так выглядит бан на прокси, а не ошибка процесса. С Mac и из облака бана нет, в том числе после 60 запросов по 6 — но порог может зависеть от адреса или сети. `/diag` делает 30 запросов подряд и 6 параллельно: если владельца отрежет посреди таблицы, будет видно, на каком запросе. Консоль Velt покажет, дошли ли запросы до процесса |
| H3 | Процесс блокирует event loop (синхронный DNS, SQLite, argon2 в одном loop с ботом) | **риск был, частично снят** | Синхронный `socket.getaddrinfo` в `_site_addresses()` вызывался на запросе раз в 10 минут — убран в фон. Монитор loop теперь пишет каждое отставание > 200 мс. Но H3 не объясняет, почему режет **одного** клиента: облако в те же минуты получало 200 |
| H4 | Клиент: Brave Shields, iCloud Private Relay, DNS-фильтр, VPN, плохой LTE | **не проверена** | Нужна матрица «браузер × сеть» и ответы владельца (раздел 5) |
| H5 | Кривой ответ (длина, сжатие) | **исключена** | curl с заголовками Safari — полный ответ; тест `payload` сверяет `Content-Length` с телом; локальный прогон в настоящем браузере — 30 из 30 |
| H6 | Хостер ограничивает входящее по IP клиента (несколько устройств за одним адресом) | **не проверена** | Наш процесс по IP не банит (см. ниже). `GET /api/diag` показывает запросов в минуту; если подтвердится по консоли — вопрос хостеру |

**Что проверено в нашем коде и отпало.** Лимит `api/__init__.py` — 300 в минуту на IP для `/api`, `/api/auth` — ещё 20 в минуту;
сверх — JSON `429 too_many`, а не обрыв и не белый экран. Статика сайта и админка без лимита. Банов по IP в сервере нет
(блокировки `bans.py` — по аккаунту, ответ `403 account_banned`). Если `SONAR_TRUSTED_PROXIES` не задан и все клиенты видны
под адресом nginx, общий лимит делят все — но и тогда сайт открывался бы, а API отвечал 429 всем сразу, не одному человеку.

## 3. Что починено и добавлено в коде

- **DNS не в запросе.** Адреса сайта для доверенного прокси (`admin/web.py`) прогреваются при старте и обновляются фоновым
  потоком `site-dns`; запрос берёт то, что уже есть (`_site_addresses`). Тест `test_request_never_waits_for_site_dns`.
- **Монитор event loop** (`sonar/diag.py` `LoopMonitor`): таймер раз в секунду, отставание > 200 мс — `WARNING sonar.diag
  event loop отстал на N мс`; max и p95 за 5 минут. Стартует с первым HTTP-запросом на том же loop, что и бот.
- **Access-лог** (`web.py` `install_access_log`) стоит самым внешним: раньше он сидел внутри раздачи сайта и писал `404` на каждую
  страницу сайта. Строка: `HTTP <метод> <путь> <IP> -> <код> <мс> мс <байт> Б[ ОБОРВАН] ua=<первые 40 знаков>`.
  `ОБОРВАН` — тело не ушло из процесса целиком (клиент или прокси закрыли соединение раньше). Nginx обычно вычитывает ответ
  сам, поэтому `ОБОРВАН` будет редким; важнее, **есть ли строка вообще**.
- **`GET /api/diag`** и **`GET /api/diag/payload?kb=N`** — API.md §12.
- **Страница `/diag`** (`sonar/diag_page.html`): один HTML без внешних ресурсов (inline CSS и JS, CSP `default-src 'none'`),
  работает без входа. Тела 1, 8, 16, 17, 32, 64, 256, 1024 КБ по три раза, каждый раз новый URL и `no-store`, потом 6 параллельных
  по 32 КБ; для каждого — исход (`ok` / `обрыв на N Б` / `таймаут` / `ошибка сети` / `HTTP xxx`), первый байт, всё время; итог одной
  строкой; «Скопировать результат» — без IP. Кнопка «Диагностика» в `/admin` бота (BOT.md §2.12в).
- **`server/tools/diag_probe.py`** — то же с командной строки, только стандартная библиотека; таблица или `--json`, код возврата 1
  при сбоях. Тесты без сети — `tests/test_diag_probe.py`.

Новых зависимостей нет. Цена на сервере: таймер раз в секунду, две очереди в памяти на 5 минут, тело `payload` считается на
лету (до 2 МБ, свой лимит 90 запросов в минуту на IP).

## 4. Если корень окажется в пути до хостинга — варианты

Выбор за владельцем. Цены — ориентиры на 2026-11-26, перед решением перепроверить.

| Вариант | Что даёт | Цена и минусы |
|---|---|---|
| Cloudflare перед доменом | Свой прокси с HTTP/2 и HTTP/3, кэш статики, другие адреса на входе | Бесплатный план — 0 ₽, но NS домена переезжают с reg.ru на Cloudflare. Если трафик владельца идёт через российскую сеть (SIM, роуминг, VPN), Cloudflare там режут сильнее всех (~16 КБ) — тогда станет хуже. Отменяет решение 2026-11-25 «Cloudflare не нужен» |
| Другой хостинг или другой IP | Уход от прокси Velt и его правил | VPS в ЕС — порядка нескольких евро в месяц, плюс переезд `sync.py`, `.env`, базы и HTTPS (свой nginx или Caddy). Сначала стоит спросить у Velt, нет ли лимита соединений на IP — может, его просто поднимут |
| Ответы меньше 16 КБ и меньше соединений на страницу | Помогает при H1 | Код: дробить ответы API, сжимать главную. Часть путей (сборки, обложки) меньше 16 КБ не сделать. Работа на клиентах и сайте, не на один вечер |
| Сжатие (gzip) на сервере | Главная 88 КБ → примерно 20 КБ, JSON — в разы | Мидлвара есть в Starlette, зависимость не нужна. При H1 не спасает, при медленной сети помогает. Самый дешёвый пункт |
| HTTP/2 на прокси | Одно соединение на всё вместо шести | Только если хостер включит; у нас в коде ничего не меняется. Спросить в поддержке Velt |
| Офлайн-устойчивость клиентов | Плохая связь не ломает приложение | Повторы с паузой и без лавины запросов после сбоя, «Проверить обновление» не дёргает всё сразу. Работа на ПК и iPhone; полезно при любой причине |

## 5. Что делает владелец

Сначала влить ветку `server-diag` в `main` и обновить сервер («Только сервер» в боте) — без этого `/diag` на проде отвечает 404.

1. На телефоне открыть `https://try-sonar.ru/diag`, нажать «Проверить», «Скопировать результат» и прислать. По очереди:
   LTE без VPN → Wi-Fi → LTE с VPN (если есть); Safari и Brave.
2. Ответить: какой оператор, страна SIM, включён ли роуминг; включены ли iCloud Private Relay, DNS-фильтр (профиль, NextDNS
   и т. п.), VPN. Часы телефона показывали UTC+3, а Латвия зимой UTC+2 — это может быть ничем, а может быть чужой SIM.
3. То же с ПК (браузер или `python server/tools/diag_probe.py`). Если ПК стабилен, а телефон нет — граница уже сужена.
4. Во время каждой попытки смотреть консоль Velt:
   - строки `HTTP GET /diag …` и дальше `/api/diag` есть, `-> 200`, байты полные → ответ ушёл из процесса, режет дальше (прокси или путь);
   - строки обрываются посреди прогона, а на телефоне `ошибка сети` / `таймаут` → клиента отрезали **до** процесса (H2 / H6);
   - есть ` ОБОРВАН` → соединение закрыли, пока мы отдавали тело;
   - есть `event loop отстал на … мс` → тормозим мы сами (H3), смотреть, что в это время делал бот.
5. Если подтвердится отрезание до процесса — спросить Velt о лимитах соединений и банах по IP на их прокси.

Когда придут таблицы — дописать сюда раздел 1.4 и статусы гипотез.
