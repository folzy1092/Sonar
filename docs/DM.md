# Личные сообщения

Из `docs/TASTE_ROOMS_PROMPT.md` §7 (2026-11-25) и ROADMAP «Личные сообщения» (идея владельца 2026-11-18): прежде всего —
**кидать другу трек** карточкой с «Играть»; звать в комнату; просто писать. **Только между друзьями** (антиспам),
поэтому у `privacy.messages` нет «Все» — только «Друзья» и «Никто».

Демо: чат с другом (трек → ответ → приглашение в комнату → трек) и чат комнаты. Отправка, ответ, правка (ПК) и удаление
своих работают в памяти; «Играть» и «В очередь» на карточке трека — настоящие, если трек есть в Любимых. Ссылка
`sonar://track/<ref>` в тексте сама превращается в карточку, если трек есть в медиатеке. Сеть не трогается.

## 1. Модель

```
DMThread  { id, peer | null, room_id | null, peer_read_at, my_read_at }
DMMessage { id, thread_id, from, text, attachments[], reply_to, sent_at, edited_at, deleted }
Attachment = track { ref, title, artist, cover_url }
           | playlist { id, title, count, cover_url }
           | room { room_id, host, title }
```

Правила ядра (их же проверит сервер):
- текст обрезается по краям; пустое без вложений не уходит; до 2000 символов (кодовых точек), до 4 вложений;
- правка — только своё, не удалённое, в течение 48 часов, вложения не меняются; удаление — своё в любое время, место в
  ленте остаётся («Сообщение удалено»);
- прочитанность — отметкой времени, а не флагом на сообщении: «прочитано» = `sent_at ≤ peer_read_at`;
- лента — по `sent_at`, повтор `id` (сервер прислал заново после обрыва) — берём последний;
- ссылки: `sonar://(track|album|playlist|room|user)/<значение>`, `encodeURI` для значения, хвостовая пунктуация не часть
  ссылки, повторы схлопываются. Чат комнаты — тот же тред с `room_id`.

## 2. Сервер (после покупки Velt)

- Хранение — SQLite: `dm_threads`, `dm_messages`, `dm_attachments` (черновик — `docs/DB.md`). **Сквозного шифрования нет** —
  написать прямо в юр-текстах (сайт `/privacy`) и в `docs/API.md`; в демо об этом строка под полем ввода.
- Срок жизни сообщений и лимиты — в `GET /config` (Velt — 2 ГБ диска, медиа не храним, только ref и метаданные).
- Пуши — через бота `@SonarMusicApp` по настройкам уведомлений; жалоба — кнопка «Пожаловаться» в боте-репортах,
  блокировка пользователя.
- Договор: `GET /dm/threads`, `GET /dm/threads/{id}/messages?before=`, `POST /dm/threads/{id}/messages`,
  `PATCH /dm/messages/{id}`, `DELETE /dm/messages/{id}`, `POST /dm/threads/{id}/read { at }`; живые новые — тем же
  WebSocket, что комнаты. Допишется в `docs/API.md`, когда начнём сервер.

## 3. Критика (честно)

- Чат в музыкальном плеере — риск сделать плохой мессенджер, которым никто не пользуется: у всех уже есть Telegram.
  Ценность только в том, чего Telegram не умеет: карточка трека, которая **играет в один тап** у друга (через его
  сервис или резерв), и приглашение в комнату. Поэтому минимум — треки и приглашения; текст — вторично, без медиа,
  стикеров и голосовых.
- Без друзей и сервера ЛС не проверить. Демо показывает вид, а не нужность.
