# Задание: что делаем, пока нет сервера (2026-11-24)

Три задачи по решению владельца (обсуждение 2026-11-24). Делать по порядку, каждую — отдельным коммитом (или
несколькими) в `main`, с тестами. Перед началом прочитать `CLAUDE.md` (тон, git, i18n, анимации, офлайн) и
`docs/HANDOFF.md`.

Общие правила, которые тут легко нарушить:
- Каждая строка интерфейса — через `t('русский текст')`, переводы на **все пять языков** (ПК `src/i18n/{en,uk,es,de,pl}`,
  iPhone — `ios/scripts/gen-i18n.mjs` + свои `Core/I18n/Strings+<Экран>.swift` с en/uk и `Strings+App{ES,DE,PL}`).
- ПК и iPhone — одна структура настроек (`docs/PLATFORMS.md`). Новая логика на iPhone — с XCTest.
- Офлайн-режим: на ПК каждая сетевая команда — через `offline::guard()`, на iPhone каждая `URLSession` — через
  `Net.configuration` (тест `testEverySessionUsesNetConfiguration`).
- Всё анимировано, всплывашки — только по клику, без «нейрослопа» (навык `unslop`: без блёсток, свечений,
  капса с разрядкой, пульса на неживых вещах).
- Проверено вживую или нет — писать честно в коммите и `HANDOFF.md`. iOS собирается только на CI (`ios.yml`).

## 1. «Проверка сервисов» на iPhone

**Зачем.** Владелец узнаёт, что сервис умер (VK — флуд-контроль после лимитов VK с 7.09.2026, Spotify — 429 на
старом API), только по окну с ошибкой. На ПК кнопка уже есть — на iPhone её нет, а структура настроек должна совпадать.

**Как сделано на ПК (образец, 2026-11-24):**
- Rust `Core::check_services` (`windows/src-tauri/src/services.rs`): у каждого **подключённого** сервиса параллельно —
  обычный поиск строки `"music"` на 1 результат (тот же путь, что поиск пользователя: ключ, сеть, сам сервис), не
  дольше 15 с. Итог по сервису — `ServiceCheck { service, ok, ms, error }`. Не подключённые не трогаем.
- Команда `check_services` (с `offline::guard()`), `api.checkServices()`.
- Интерфейс: Настройки → Сервисы, карточка «Проверка сервисов» под карточками сервисов
  (`windows/src/pages/settings/Services.svelte`): кнопка «Проверить» / «Проверяю…», по каждому — точка
  (`--online` / `--danger`), имя, «Работает · {sec} с» или текст ошибки; «Ни один сервис не подключён». В офлайне —
  неактивна. Строки уже переведены (ключи: «Проверка сервисов», «Каждый подключённый сервис ищет одну строку — видно,
  жив ли ключ и отвечает ли сервис», «Проверить», «Проверяю…», «Ни один сервис не подключён», «Работает · {sec} с») —
  после `node ios/scripts/gen-i18n.mjs` они появятся в словарях iPhone сами.

**Сделать на iPhone:**
- Чистая логика в `Core/` (например `Core/Services/ServiceCheck.swift`): вход — список подключённых сервисов и
  функция поиска, выход — `[ServiceCheck]`; параллельно (`withTaskGroup`), тайм-аут 15 с на сервис, время в мс.
  Поиск — тот же, что в «Поиске» (`MusicCore`, по сервису). XCTest на поддельном поиске: успех, ошибка, тайм-аут,
  пустой список, порядок как в реестре (`ServiceRegistry`).
- Экран: `Features/Settings/ServicesView.swift` — карточка внизу, как на ПК (кнопка, строки, анимация появления).
  В офлайне (`OfflineFlag`) — неактивна с подписью «Недоступно в офлайне».
- **Не делать:** отдельный экран, проверку текстов (lrclib/Genius) — только музыкальные сервисы.

**Готово, когда:** на iPhone есть та же карточка, XCTest зелёный на CI, `docs/PLATFORMS.md` отмечает паритет.

## 2. Полное сведение на iPhone для потоков HLS SoundCloud

**Проблема (BLEND §13).** На iPhone большинство треков SoundCloud играют потоком HLS. `AudioTap` (обработка звука:
фильтры, эквалайзер, эхо, сдвиг тона) к HLS-потоку в AVFoundation не подключается, поэтому в переходе сведения у
таких треков работает только громкость (`BlendPlayerDeck` шагает её раз в 50 мс). Анализ при этом уже есть:
`BlendAnalysisStore` склеивает HLS SoundCloud во временный файл (тем же путём, что «Скачать»: `MusicCore.downloadSource`
+ `CoreDownloadFetcher`), анализирует и **стирает** файл.

**Идея.** Когда сведение включено, дек играет **склеенный файл**, а не поток — тогда `AudioTap` подключается и
переход звучит как на ПК.

**Сделать:**
- Склеенный файл не стирать сразу после анализа, а класть в кэш треков (`WaveCache` или общий кэш, где уже лежат
  файлы для офлайна) с обычным вытеснением по размеру. Повторный анализ и игра берут его оттуда.
- `PlaybackEngine`: если `blendOn` и для трека SoundCloud есть локальный склеенный файл — грузить в дек его
  (как скачанный трек), а не HLS. Нет файла к моменту загрузки B — склеить заранее: преролл сведения на ПК
  начинается за 8 с до перехода (`PREROLL_SEC`), на iPhone — заранее, вместе с анализом следующего трека.
  Не успели — прежний путь (HLS, только громкость), без ошибок и пауз.
- Текущий трек A, если он начинал играть потоком, **не перезапускать** посреди прослушивания: полное сведение — для
  треков, которые начались из файла (следующий после первого перехода уже будет из файла).
- Учесть лимиты: `BlendAnalysisFiles.maxDownloadBytes` (60 МБ), `maxDurationMs` (20 мин), «Только по Wi‑Fi» для
  скачиваний (`DownloadPlan`), офлайн — только уже склеенное.
- Обновить `docs/BLEND.md` §13 (что теперь звучит полностью, что нет), убрать подсказку в `BlendSheet` про
  «только громкость», когда трек из файла.

**Проверка.** XCTest на выбор источника (файл / HLS / нет файла — откат) и на кэш склеенных файлов (кладём,
находим, вытесняем). Вживую — только владелец на телефоне: переход «Фильтр» и «Эхо» между двумя треками
SoundCloud должен звучать с фильтром и хвостом эха, а не просто громкостью.

## 3. Синхронизация ПК ↔ телефон по Wi‑Fi — временно, вместо сервера

**Решение владельца:** это не самостоятельная фича, а затычка до сервера (он скоро). Там, где потом будут кнопки
«отправить на сервер / забрать с сервера», пока работает обмен по Wi‑Fi. Ничего не придумывать сверх того, что
сервер потом заменит один к одному. **Без привязки к iPhone** — будет ещё Android, протокол должен подойти ему.

**Что уже есть (не писать заново):**
- Синхронизация на клиентах в формате сервера (API.md §6): ПК `windows/src-tauri/src/store/sync.rs` (что
  отправлять: всё, у чего `rev` новее `pushed_rev`) + `sync.rs` (обмен `POST /sync/push`, `GET /sync/pull?since=`,
  тесты на `MemoryServer` — два устройства одного аккаунта меняются лайками, плейлистами, настройками и журналом
  волны); iPhone `Core/Sync/` (`SyncEngine`, `SyncService` — сейчас включается только при `AccountStore.serverEnabled`).
- Пульт по Wi‑Fi (API.md §10): ПК поднимает WebSocket-сервер в локальной сети (`windows/src-tauri/src/remote/`,
  порт 53120, mDNS `_sonar._tcp`, привязка телефона кодом/QR, список устройств `devices.rs`); iPhone `Core/Remote/`.

**Идея реализации.** ПК временно сам отвечает как сервер синхронизации: те же `sync/pull` и `sync/push` (тела и
ответы — строго как в API.md §6), только для привязанных через «Пульт» устройств и только в локальной сети. Логика
«сервера» — как у `MemoryServer` (журнал операций с `rev`, правило «кто позже» по `client_ts` для настроек), но
поверх базы ПК: устройство ПК тоже участник, его изменения видны телефону.
- Транспорт — тот же, что у пульта: либо новые типы сообщений в WebSocket пульта, либо HTTP на том же порту с ключом
  привязки. Выбрать то, что проще проверить тестами; обосновать в коммите.
- Телефон: `SyncService` получает второй «адрес сервера» — привязанный ПК. Если настоящего сервера нет, но ПК
  привязан и найден в сети — синхронизироваться с ним. Появится сервер — этот путь просто не включается.
- Интерфейс — минимальный, где будут серверные кнопки: на ПК в «Система → Пульт» и на телефоне в его настройках
  пульта — строка «Синхронизация с телефоном / с ПК» (последний обмен, «Синхронизировать сейчас»). Никаких отдельных
  разделов. Подсказка: «Пока нет сервера Sonar — лайки, плейлисты и настройки едут по Wi‑Fi».

**Перенос скачанного (идея 2 владельца) — в эту же задачу, но вторым шагом и только если первый шаг готов:**
телефон может попросить у ПК файл скачанного трека (тот же канал, только привязанным устройствам, по одному файлу,
с докачкой). Если выходит больше, чем на день, — не делать, записать в `HANDOFF.md`.

**Проверка.** Rust-тесты: ПК как сервер — два клиента (ПК и «телефон» на `MemoryServer`-подобной заглушке)
обмениваются лайком, плейлистом, настройкой, конфликт настроек по `client_ts`; чужое (не привязанное) устройство
получает отказ. XCTest: `SyncService` выбирает ПК, когда сервера нет, и не трогает его, когда сервер есть.
Вживую — владелец: лайк на ПК → через минуту есть на телефоне, и наоборот.

**Не делать:** синхронизацию через интернет, свой облачный ретранслятор, шифрование поверх того, что уже даёт
привязка пульта, синхронизацию между двумя ПК.
