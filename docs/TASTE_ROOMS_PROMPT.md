## 1. Вкус: «больше / меньше / никогда» по артисту

**Зачем.** Сейчас у Sonar Mix есть 👎 на треке и пауза артиста до конца сессии, но нет постоянного слова «этого артиста
больше», «меньше» или «никогда». У Dotify это экран вкуса (1.4.0). Это самая дешёвая и полезная часть их списка: сигналы
у нас уже собираются, не хватает ручки.

**Данные.** Одна настройка `wave.artist_prefs` (ПК и iPhone, едет по синку настроек «побеждает позднее»):
```json
{ "markul": { "name": "Markul", "level": "more" }, "oxxxymiron": { "name": "Oxxxymiron", "level": "never" } }
```
Ключ — имя артиста в нижнем регистре и без пробелов по краям, **ровно как `wave::artist_keys`** (имена из `track.artists`,
а если список пуст — строка `track.artist`). `level`: `more` / `less` / `never`. Нет записи — ничего не задано.
Нет миграции БД. Минус: два устройства меняют разные артисты одновременно — побеждает позднее целиком; для друзей и
одного владельца это приемлемо, но записать в `docs/SETTINGS.md`.

**Поведение (бэкенд на ПК уже в коде):**
- `never` — трек не попадает в порцию волны ни в `pick`, ни в `pick_liked`, даже если артист — соавтор.
- `more` / `less` — признак `pref` = +1 / −1 с весом `PREF_WEIGHT = 2.0` во всех режимах (как лайкнутый артист в
  «Обычном»). `more` любого из соавторов перебивает `less`.
- Автоплей похожих (`player/autoplay.svelte.ts`, iPhone `Autoplay.swift`): `never` пропускать так же, как 👎
  (`freshSimilar` получает ещё один предикат). `more` / `less` в автоплее не учитывать — там нет оценки.
- Лайк артиста или трека `never` не запрещает: это ручное действие, оно главнее.

**Сделать на ПК:**
1. Ключ `wave.artist_prefs` в `windows/src/lib/settings.svelte.ts` (`DEFAULTS`, тип `Record<string, ArtistPref>`), пункт в
   `settings-catalog.ts`, строка в `docs/SETTINGS.md`. Тест `settings-catalog.test.ts` требует, чтобы ключ был в `DEFAULTS`.
2. Чистое ядро `lib/artist-prefs-core.ts` + тесты: `artistKey(name)`, `trackKeys(track)` (зеркало Rust),
   `levelFor(prefs, track)` (`never` > `more` > `less`), `withLevel(prefs, name, level | null)`. Реактивная обёртка —
   `lib/artist-prefs.svelte.ts`.
3. Меню трека (`app/TrackMenu.svelte`, рядом с «Не нравится»): три пункта «Больше этого артиста», «Меньше…», «Никогда…» с
   отметкой текущего. У совместного трека — по главному артисту (`artists[0]`). То же — в меню страницы исполнителя.
4. Страница **«Вкус»** — подраздел вкладки «Плеер» (`pages/settings-section.svelte.ts`, `SUBS.player`, строка в `SUB_LEADS`):
   - список артистов с этой настройкой: имя, переключатель из трёх положений + «убрать»; сверху поиск по списку;
   - ниже — список 👎-треков (`api.dislikedRefs()` → `api.cachedTracks(refs)`), у каждого «вернуть»;
   - анимации по правилам проекта (`use:cascade`, `use:indicator`), всплывашек нет.
   Не делать: «оттенки раскрываются по нажатию» из Dotify — у нас нет такого профиля, выдумывать не надо.
5. Предпросмотр порции волны (`my-wave.svelte.ts` → `api.wavePortion`) уже идёт через тот же Rust, отдельной работы нет.

**iPhone:** найти, где волна считается на телефоне (`Core/…` порт `wave.rs` — начать с `grep -rn "paused" ios/Sonar/Core`), и
повторить `never` / `pref`. Если волна на iPhone — упрощённая копия без `Features`, делать только `never` и
вес `more` / `less` там, где есть оценка. Экран — `Features/Settings/…`, строки — `Strings+<Экран>.swift`. XCTest обязателен.

**Критика идеи.** Хорошая и дешёвая. Риск один: `never` при малом числе знакомых артистов оставит пустую порцию — у
`pick` уже есть ослабленный проход (`relaxed`), он `never` не ослабляет, и это правильно, но проверить, что волна не
зависает на пустом пуле, тестом.

## 3. Баг: очередь не отделяет «похожие» от плейлиста (сделано, проверить вживую)

**Жалоба владельца (ПК и iPhone).** Включено «Авто похожие»: доиграл плейлист — и дальше как будто продолжается тот же
плейлист, граница не видна.

**Причина.**
- ПК: боковая панель (`app/SidePane.svelte`) не рисовала строку `switch` («Авто похожие»), которую выдаёт

- iPhone: `QueueSheet` показывал тумблер **над** «Далее», а свои и похожие треки шли одним списком.

**Сделано:** ПК — черта «Пошли похожие» в «Ранее» / перед «Сейчас играет», строка тумблера в боковой панели, плашка

(`engine.contextLabel`). Правила: черта рисуется, только если до первого похожего видно что-то из своего.

**Проверить вживую:** (а) плейлист из 3 треков, автоплей включён — после третьего в боковой панели и в «Очереди» видна

(г) Sonar Mix — без черты. Отдельный вопрос, который прошлая сессия **не проверяла**: не попадают ли в «похожие» треки,
которые уже есть в плейлисте, но не загружены в очередь (страница плейлиста грузит куски?). `freshSimilar` исключает только то,

## 6. Комнаты совместного прослушивания («как Rave, но для музыки»)

**Желание владельца.** Сервис вроде Rave (совместный просмотр фильмов), только для песен: пригласить друга и слушать **в одно
и то же время** плейлист или конкретную очередь. Включить свои любимые, любимые друга или что-то ещё.

**Рамки (из CLAUDE.md, не переигрывать):** сервер аудио **не хранит и не отдаёт** (решение 2026-11-19). Каждый играет
через свой аккаунт и со своего IP. Значит комната синхронизирует **состояние**, а не звук. Нужен сервер (Velt, WebSocket),
поэтому сетевую часть делать **после** покупки сервера. Друзья и ЛС — решение 2026-11-18: «делаем с сервером».

### 6.1. Модель комнаты
```
Room { id, host, leader, djs[], members[], source, queue[{ref,added_by}], pos, playing,
       anchor { server_ts_ms, position_ms }, rev, closed }
```
Роли: **хост** (создал, может закрыть), **лидер** (чьи Play/Pause/перемотка главные; по умолчанию хост; хост передаёт),
**диджей** (добавляет, переставляет, удаляет треки очереди), **слушатель** (слушает, может предлагать треки). У Dotify это
есть с 1.2.2 / 2.3.4 / 1.4.0 (передача лидерства, диджеи, закрытие комнаты, «предложить трек»).

Источник очереди при создании: мои Любимые · Любимые друга · плейлист (мой или друга) · текущая очередь · Sonar Mix по
двоим (вкус обоих — отдельная приятная штука, но потом). Очередь живёт на сервере как список `ref`, не файлов.

### 6.2. Синхронизация (самое сложное)
- Сервер хранит **якорь**: `(server_ts, position_ms)` в момент, когда лидер нажал Play / перемотал. Позиция сейчас =
  `anchor.position + (server_now − anchor.server_ts)`, пока `playing`.
- Клиент мерит смещение часов с сервером (NTP-подобно: 4–5 пингов, берётся минимальный RTT), пересчитывает позицию и
  подстраивается: расхождение < 250 мс — не трогать; 250 мс … 2 с — плавная подстройка скорости ±3 %; больше — `seek`.
- Начало трека: у всех разный старт потока (HLS SoundCloud, mp3 Яндекса) — общий момент старта назначается на
  `server_now + 1.5 с`, клиент заранее прогревает поток (`preload`) и стартует, когда готов, догоняя подстройкой.
- Один и тот же трек в Яндексе и SoundCloud может отличаться вступлением на секунды — допуск и кнопка «Синхронизировать»
  у слушателя (ручной ресинк по якорю).
- Недоступный у слушателя трек: резерв (`services/fallback.rs`, iPhone `Fallback.swift`); нет и резерва — слушатель молча
  пропускает до следующего, в комнате ему видно «нет трека у тебя».
- Комната, где лидер не играет, открывается на паузе; зашедший сразу слышит текущий трек (то же в патче 1.3.0 у Dotify).
- Звук (эквалайзер, скорость, пространство): у Dotify «звук комнаты берётся из настроек хоста». Рекомендация: **у каждого
  свой** (устройство, наушники и вкус разные), общей остаётся только скорость 1×; иначе синхронизация ломается. Решение за
  владельцем.

### 6.3. Протокол (дополнить `docs/API.md`)
WebSocket `/rooms/{id}`; сообщения: `join`, `leave`, `state` (полный снимок с `rev`), `op` (`play`, `pause`, `seek`, `next`,
`prev`, `queue.add`, `queue.remove`, `queue.move`, `leader.set`, `dj.set`, `close`), `suggest`, `ping/pong`. Сервер — источник
истины, последовательность по `rev`, клиент после обрыва делает `join` и получает `state`. Права ролей проверяются на
сервере. Приватность: `privacy.*` — кто может звать в комнату (все / друзья / никто), видна ли твоя комната друзьям.
У Dotify в 1.4.0 появилась отдельная приватность очереди, совместного прослушивания и устройства — добавить как три
переключателя в «Приватность» (`pages/settings/Privacy.svelte`, `Core/Account/Privacy.swift`).

Нагрузка: Velt 512 МБ / 25 % vCPU. Комнат у владельца и друзей единицы, сообщения — десятки байт; один процесс бота с
`websockets` это держит. Лимит комнат и участников — в `GET /config` (по умолчанию участников 8 — как «Вечеринка» у Dotify).

### 6.4. Что делать **до сервера**
- Чистое ядро, без сети, с тестами на ПК (vitest) и iPhone (XCTest): конечный автомат комнаты (роли, права, `rev`),
  расчёт позиции по якорю, оценка смещения часов, решение «ничего / подстроить / seek».
- Интерфейс на демо-данных, как сделана «Схожесть» (демо-друг в предпросмотре «Друг»): экран комнаты, список участников с
  ролями, очередь с «кто добавил» (в совместных плейлистах это уже есть — `playlist_items.added_by`), кнопки ролей.
  «Создать комнату» и «Пригласить» неактивны, как «Пригласить друга» в совместном плейлисте.
- Прототип протокола можно прогнать по **уже существующей связи ПК ↔ iPhone по Wi‑Fi** (`remote/`, WebSocket с
  привязкой кодом): два устройства владельца слушают синхронно. Это даёт настоящую проверку синхронизации (дрейф,
  ресинк) без сервера. Главный практический вопрос всей затеи — точность на реальных потоках; её надо мерить раньше UI.

### 6.5. Критика
- Идея сильная и в духе проекта, но это **самая рискованная** часть списка: синхронизация на разных сервисах и устройствах
  всегда «плывёт», обещать «в одно и то же время» можно с допуском в сотни миллисекунд, не точнее. Мерить до интерфейса.
- Всё упирается в сервер и в друзей. Без ЛС и друзей комната — просто ссылка; поэтому порядок такой: сервер → друзья и ЛС →
  комнаты. Не наоборот.
- «Любимые друга» требует, чтобы у друга эти любимые были открыты (`privacy.*`) и чтобы у слушателя играли его треки
  (резерв делает это в большинстве случаев).

## 7. Личные сообщения (с сервером)

Нужны, чтобы **кидать другу треки** (находятся поиском), **звать в комнаты** и просто писать. По Dotify (2.3.3): чаты единые —
личные сообщения и чат активной комнаты на одной системе; затем 1.2.3 «прикрепить текущий трек», 2.3.4 «ответы на сообщения,
прикрепить плейлист», 1.4.0 «правка своих сообщений».

Минимум первой версии: текст; вложение «трек» (из поиска и «текущий») с кнопками «играть», «в очередь», «в Любимые»;
вложение «приглашение в комнату» (карточка с «Войти»); ответ на сообщение; правка и удаление своих; статус «прочитано»;
пуши через бота `@SonarMusicApp` (по настройкам уведомлений). Хранение — SQLite на сервере, сообщения не шифруем сквозным
(написать это прямо в юр-текстах и в `docs/API.md`). Чат комнаты — тот же механизм, привязанный к `room_id`.
Спам и жалобы — кнопка «Пожаловаться» в боте-репортах, блокировка пользователя. Договор — `docs/API.md` (новая секция),
схема — `docs/DB.md` (`dm_threads`, `dm_messages`, `dm_attachments`), настройки — `privacy.*` («кто может писать»).

До сервера: только ядро (структуры вложений, разбор «трек из чата» → `sonar://track/<ref>`) и экраны на демо-данных.
